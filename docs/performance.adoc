= Производительность и размер WASM

`adoctra-performance-v1` — воспроизводимый стенд для базовых измерений этапов
7–8. Он измеряет native-вызовы внутри одного процесса и размер release-модуля
WASM. Это отдельный отчёт, без порогов скорости и без утверждения о соответствии
языка: семантику проверяют link:compatibility.adoc[сравнительные профили].

== Запуск

Требуются Rust/Cargo из `rust-toolchain.toml`, Python 3.10+ и установленный
`wasm32-unknown-unknown`. Ruby, сетевые ресурсы документов и Python-пакеты
не используются. Первая сборка может потребовать загрузки зависимостей Cargo;
`--locked` сохраняет версии из `Cargo.lock`.

[source,shell]
----
rustup target add wasm32-unknown-unknown
python3 scripts/performance.py --output target/performance/report.json
----

Скрипт сам собирает release-пример `adoctra-json/examples/performance.rs` и
release `adoctra-wasm`, получает пути артефактов из JSON-сообщений Cargo.
Библиотеки и граф зависимостей не меняются, новых зависимостей нет.
По умолчанию выполняются 2 прогревочных вызова каждой операции, затем 5 выборок
по 3 вызова. Прогревочные вызовы не входят в результат. Время — монотонный
`Instant`, в отчёте сохранены целые наносекунды каждой выборки и число повторов.

[source,shell]
----
# Короткая проверка стенда: два реальных документа и четыре малых стресс-входа.
python3 scripts/performance.py --smoke --samples 1 --iterations 1 --warmup 0 --skip-wasm

# Выбранные входы, больше выборок; --case можно повторять.
python3 scripts/performance.py --case spring-webtestclient --case stress-references-512 --samples 9 --iterations 5 --output target/performance/selected.json
----

`--timeout` ограничивает каждый процесс измерения (по умолчанию 180 секунд),
`--skip-wasm` явно записывает `status: skipped`. Неизвестный case, debug-сборка,
неверные размеры входов, неполные измерения, падение процесса или таймаут
останавливают запуск. Warning/error на обычном входе также считаются ошибкой;
диагностики намеренно незавершённого документа сохраняются в отчёте.
Прежний файл отчёта заменяется атомарно только после успешного полного запуска.

== Что измеряется

[cols="1,3",options="header"]
|===
|Операция |Границы таймера
|`parse`
|Свежий `SourceMap`, регистрация основного UTF-8-буфера, `parse_resource`,
уничтожение результата и карты источников.
|`tokens`
|Свежий `SourceMap`, регистрация, `tokens_resource` и уничтожение результата.
Текущий API выполняет полный разбор; это полная стоимость запроса подсветки,
а не отдельный проход лексера поверх уже готового AST.
|`json`
|`JsonBackend::convert` готового AST и уничтожение JSON-буфера. AST получен
один раз до замеров. Снимки атрибутов и редакторский JSON/WASM не сериализуются.
|`parse-json`
|Свежая карта источников, полный разбор и `JsonBackend::convert`, уничтожение
AST, JSON-буфера и карты источников.
|===

Чтение файлов с диска, создание provider, сборка, запуск процесса, проверочный
разбор и печать результата находятся вне таймеров. Копирование исходного буфера,
построение индекса строк, загрузка include из `MemoryResources`, выделение и
освобождение памяти находятся внутри соответствующих операций. Результат
передаётся в `black_box`; значения не накапливаются между итерациями.
У каждого вызова свежие source IDs и состояние счётчиков. Операции запускаются
в фиксированном порядке `parse`, `tokens`, `json`, `parse-json`.

Отчёт хранит median/min/max и MAD (медиану абсолютных отклонений) в наносекундах
на один вызов: сначала каждая выборка делится на число повторов. Отдельно
сохраняются размеры входов, число корневых блоков, токенов, байтов JSON и
диагностик по severity. Это контроль состава работы, а не семантический эталон.
Входные байты include считаются один раз на предоставленный ресурс, а не по
числу его раскрытий. Основной стенд не измеряет память/RSS и число аллокаций;
отдельное исследование аллокаций описано ниже.

== Входы и воспроизводимость

* 12 полных страниц из `compatibility/acceptance/semantics.json`: шесть
  Asciidoctor 2.0.23 и шесть Spring Framework 6.2.0. Используются те же исходные
  байты, include-ресурсы и host-атрибуты; SHA-256, происхождение и лицензии
  проверяются существующим загрузчиком корпуса до сборки. Входы не копируются
  в новый корпус и не сокращаются. Safe/secure и `embedded + showtitle`
  соответствуют приёмке. Provider использует виртуальный `/main.adoc`:
  built-in пути виртуальны, файлового/сетевого I/O процессора нет.
* 12 синтетических входов: четыре семейства по 32, 128 и 512 единиц.
  `prose` — Unicode, форматирование и ссылки; `references` — атрибуты,
  разделы, циклически замкнутые xref и именованные сноски; `tables` — три
  столбца и AsciiDoc-ячейки со списками; `incomplete` — незакрытые inline
  конструкции и незавершённый listing. Генерация детерминирована и версионирована
  как `synthetic-v1`. Глубокая вложенность и fuzzing в этот набор не входят.

Для каждого входа сохраняются SHA-256 основного текста и ресурсов. Отчёт также
содержит git revision/dirty, общий fingerprint Rust-исходников, Cargo manifests,
lockfile, toolchain, локального Cargo config и самого Python-стенда; SHA-256
native/WASM артефактов; версии Rust/Cargo/Python, ОС/архитектуру, модель CPU,
число доступных CPU/affinity, load average и заданные build flags.
Если fingerprint меняется во время измерений, отчёт не записывается.
`stable` — плавающая версия toolchain: для повторения конкретного результата
используйте версию `rustc`, записанную в отчёте, и те же настройки сборки.
Пользовательские настройки Cargo вне репозитория нужно контролировать отдельно.

Запускайте измерения отдельно от сборок и тестов, на одной машине и с одинаковой
affinity/режимом питания. При необходимости ограничьте CPU внешним `taskset`;
доступная affinity попадёт в отчёт. Сравнивайте несколько полных запусков и
исходные выборки. Один результат на общей CI-машине не доказывает регрессию;
особенно не следует интерпретировать небольшую разницу `parse` и `tokens`
как разницу алгоритмов без профилирования.

== Размер WASM

Измеряется `.wasm`, созданный `cargo build --locked --release -p adoctra-wasm
--target wasm32-unknown-unknown`: исходный cdylib *до* `wasm-bindgen`, упаковки
и `wasm-opt`. Записываются размер в байтах, SHA-256 и размер gzip уровня 9 с
нулевым timestamp, вместе с версией zlib. Заголовок WASM проверяется.
Это не размер готового web-пакета: JS glue, доставка по HTTP, browser runtime
и скорость выполнения WASM не измеряются. Размер native executable также
не используется как показатель производительности.

== Автоматические проверки

Основной CI выполняет Rust-тесты драйвера, Python-тесты статистики/протокола,
проверки происхождения, передачи UTF-8/CRLF и include, неверных параметров,
таймаутов и атомарной записи. Затем запускается release smoke без WASM;
порогов длительности нет. `performance.yml` запускается вручную через
`workflow_dispatch`, измеряет все 24 входа и WASM, публикует JSON как artifact.
Он не запускается по расписанию и не блокирует изменения из-за скорости машины.

== Профилирование одной операции

Пример `performance` принимает `--profile-operation parse` либо `tokens`.
В этом режиме выполняется только выбранная операция с указанными
`--warmup`, `--samples`, `--iterations`; проверочных разборов и JSON-конвертации
нет. Чтение входов, создание provider и вывод результата остаются в процессе,
поэтому внешний profiler видит также эти накладные расходы.
Выход имеет отдельную схему `adoctra-profile-driver-v1` и не принимается
основным стендом как обычный отчёт измерений. Профиль не проверяет семантику
и отсутствие диагностик; проверяйте входы обычным стендом и приёмкой.

Пример для Linux с установленными GNU gprofng и glibc `libmemusage.so`:

[source,shell]
----
mkdir -p target/profiling
PYTHONPATH=scripts python3 -c 'from performance import synthetic; from pathlib import Path; Path("target/profiling/references.adoc").write_text(synthetic("references", 512), encoding="utf-8")'
CARGO_TARGET_DIR=target/profile CARGO_PROFILE_RELEASE_DEBUG=1 RUSTFLAGS='-C dwarf-version=4 -C force-frame-pointers=yes' cargo build --locked --release -p adoctra-json --example performance

# CPU: повторение одной операции; перед интерпретацией обязательно читать header.
gprofng collect app -p hi -o target/profiling/cpu.er target/profile/release/examples/performance --source target/profiling/references.adoc --profile-operation parse --warmup 0 --samples 1 --iterations 100
gprofng display text -header -limit 30 -functions -calltree target/profiling/cpu.er

# Стэки аллокаций: дорогое инструментирование, достаточно одного вызова.
gprofng collect app -p off -H on -o target/profiling/heap.er target/profile/release/examples/performance --source target/profiling/references.adoc --profile-operation parse --warmup 0 --samples 1 --iterations 1
gprofng display text -header -limit 30 -metrics i+heapallocbytes:i+heapalloccnt:name -functions -allocs target/profiling/heap.er

# Независимые счётчики glibc. Путь зависит от дистрибутива/архитектуры.
LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libmemusage.so target/profile/release/examples/performance --source target/profiling/references.adoc --profile-operation parse --warmup 0 --samples 1 --iterations 1
----

Для подсветки замените операцию на `tokens`, для таблиц — генератор на `tables`.
Храните отдельные исполняемые файлы до/после изменения до завершения профилей:
gprofng архивирует их при выходе. Не сравнивайте времена инструментированных
запусков с native timing. Библиотека `libmemusage` подключается только к
процессу драйвера; не экспортируйте `LD_PRELOAD` на весь запуск Cargo/Python.

== Устранение временных буферов substitutions

После начальной базовой линии выполнены повторные полные native-прогоны
на CPU 2 и исследованы `references`/`tables` по 512 единиц. Профиль стеков
аллокаций показал создание временного `Text` ради одного source span и
пересоздание вектора фрагментов в `restore_boundaries`, когда восстанавливать
разделённую разметку не требуется.

`replacement_origin` теперь вычисляет владельца и физический span напрямую;
им пользуются обычная замена, `match_span`, `replace_parts` и `replace_ui`.
`restore_boundaries` возвращается сразу, если нет разделённых semantic boundaries.
Правила substitutions, source ownership и экспортируемый AST не меняются.
Проверены Unicode/CRLF, происхождение атрибутов, изменение id/role,
raw-разметка и невидимые indexterm; существующие HTML/семантические/позиционные
корпуса проходят без изменения эталонов.

В этом окружении gprofng 2.44 сообщает `Collection interval timer period was
changed`; CPU-время и процентные доли из него не используются для выводов.
Стэки аллокаций служат для локализации, итоговые счётчики отдельно проверяются
glibc `libmemusage`. Его `heap total` и количество `malloc + realloc + calloc`
характеризуют работу аллокатора за весь процесс, включая загрузку/вывод.
Это не RSS и не объём живого AST. Значения `heap total` разных инструментов
не смешиваются: они по-разному учитывают realloc. Пиковая память и выводы
об утечках из gprofng в этом окружении не используются.

link:../performance/substitution-buffers.json[Исходные данные исследования]
содержат все 24 входа, три полных прогона каждой версии и три дополнительные
пары на двух больших стресс-входах (порядок до/после, после/до, до/после).
В каждом прогоне — 5 выборок по 3 вызова и 2 прогрева. Входы и наблюдаемые
результаты до/после совпадают. Для профилирования сохранены команды,
fingerprints исполняемых файлов и
link:../performance/profiles/heap-before-references-parse.txt[стэки аллокаций],
а также четыре CPU-профиля с исходными предупреждениями.
