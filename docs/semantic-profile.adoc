= Inline-семантика и снимки атрибутов

`inline-semantics-v1` — отдельный ограниченный профиль совместимости
с Asciidoctor 2.0.23. Он сравнивает разрешённое inline-дерево и явно выбранные
атрибуты независимо от HTML backend. Это не официальный ASG/TCK и не полный
контракт всех узлов AsciiDoc.

Начальная выборка `compatibility/upstream/semantics.json` содержит 38 PASS:
20 атрибутных и 4 include-сценария из существующего upstream-корпуса, плюс
14 собственных семантических проб. Upstream-входы, ресурсы и сведения о
происхождении используются без изменения; собственные пробы помечены отдельным
origin. Новые входы и ресурсы имеют SHA-256. Эталоны хранятся отдельно от HTML
под именами `reference/semantic-*.json`.

== Независимый эталон

В Ruby inline-узлы создаются при substitutions, а не сохраняются готовым деревом
после `load`. `scripts/asciidoctor-semantics.rb` реализует собственный converter
с backend traits html5 и сохраняет семантические узлы из этих callback.
HTML converter не вызывается; проверка эталона запрещает его вызов подменой
метода, которая выбрасывает исключение.

Форматирование и ссылки возвращают парные служебные границы вокруг исходного
содержимого. Это оставляет содержимое доступным следующим стадиям: в
`*{who} https://example.org*` должны выполниться attributes и macros после quotes.
Границы используют угловые разделители, чтобы URL-сканер не поглотил окончание
узла, и зарезервированные U+E000/U+E001. Они разбираются как собственный протокол,
без HTML-парсера. Литералы с этими символами во входах, ресурсах или host-значениях
отклоняются, неизвестные/несбалансированные границы вызывают ошибку.

`scripts/semantics.py` адаптирует JSON AST adoctra. Узлы `substituted` и
семантические `parts` собираются в дерево; открытие и закрытие форматирования
могут находиться в разных соседних inline-узлах. Лексические entities из Ruby
и `Raw`-частей декодируются однократно, обычные `Text`-значения не декодируются.
Соседние текстовые узлы объединяются. В обычном тексте пробелы, табуляции и
переводы строк согласуются в один пробел, а явный перенос сохраняется отдельным
`line-break`. В выбранных значениях атрибутов пробелы сохраняются.

== Схема и границы

Сравниваются:

* Название документа, параграфы, разделы, preamble и составные open-блоки:
  порядок/вложенность, уровни разделов, id/roles и названия блоков.
* Текст, strong/emphasis/monospace/mark/superscript/subscript/span, id/roles
  форматирования, ссылки с разрешённой целью и inline-меткой, anchor,
  xref с явно заданной меткой и явные переводы строк.
* Атрибуты, перечисленные в `semantic_attributes` каждого сценария: снимок
  после чтения header и после обхода тела с replay записей и substitutions.
  Отсутствие (`null`), пустое значение (`[]`), текст и форматированные части
  различаются. Неперечисленные атрибуты, включая часы и локальные пути, не сравниваются.

Ссылочный признак `bare` не сравнивается; target и содержимое сравниваются.
Поля refid/path/fragment у xref не являются отдельными утверждениями профиля:
проверяется итоговый target. Ссылочные id/roles (кроме `bare`), title/window/rel,
неявные метки xref, изображения, UI/stem/indexterm/footnotes/callouts, списки,
таблицы и прочие контейнеры требуют расширения схемы. Raw HTML и неэкранированный
`<` в лексическом потоке отклоняются. Пробы с повторным экранированием результата
converter (например, quotes перед specialcharacters в явно заданных subs)
не входят в начальную выборку; служебные границы не моделируют конкретные HTML-теги.

Неизвестные контексты, виды частей и неверная схема вызывают ошибку стенда,
а не пропускаются. Warning/error/fatal/unknown также останавливают этот профиль:
их нельзя потерять при сравнении семантики. Диагностики остаются в существующем
HTML-профиле; их позиции и source spans здесь не сравниваются. PASS не означает
совпадения всей семантики языка или полного набора атрибутов.

== Экспорт атрибутов adoctra

`JsonBackend::convert_with_attributes(&document)` добавляет к обычному JSON AST
объект `attribute_snapshots` с полями `header` и `final`. Каждый снимок содержит
`values` со строковыми значениями и, при наличии, `attribute_parts` с тем же
форматом семантических частей, который используется редакторским API.
По умолчанию JSON backend сохраняет прежний формат.

CLI включает экспорт явно:

[source,shell]
----
adoctra input.adoc --to json --json-attributes --stdout
----

С другим backend флаг возвращает ошибку. Все атрибуты экспортируются, а
сравнительный адаптер выбирает только перечисленные в сценарии имена.

== Проверка

[source,shell]
----
cargo build -p adoctra-cli
python3 scripts/acceptance.py --manifest compatibility/upstream/semantics.json
python3 scripts/acceptance.py --manifest compatibility/upstream/semantics.json --verify-reference
python3 scripts/acceptance.py --manifest compatibility/upstream/semantics.json --json-report target/semantics-report.json
ruby scripts/test_asciidoctor_semantics.rb
python3 -m unittest discover -s scripts -p 'test_*.py'
----

Offline-запуск не требует Ruby. `--verify-reference` пересчитывает результат
эталона и отвергает дрейф. `--update-reference` используется только для осознанного
обновления после проверки diff. Для известных расхождений доступны XFAIL с
полным baseline, проверка регрессии и XPASS; в начальной выборке XFAIL нет.
Ошибка процесса или неподдерживаемая конструкция не считается XFAIL.
Оба режима, тесты адаптера и отдельные Ruby-проверки converter включены в CI.
