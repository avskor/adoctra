= Приёмочный корпус

Стенд `scripts/acceptance.py` дополняет минимальные сравнительные сценарии
полными документами и отдельной проверкой диагностик. Манифест:
link:../compatibility/acceptance/cases.json[compatibility/acceptance/cases.json].
Эталон — тот же закреплённый Asciidoctor 2.0.23.

== Документы и происхождение

Исходные файлы хранятся в `compatibility/acceptance/sources/`. Каждый имеет
SHA-256 и ссылку на запись происхождения в манифесте. Файлы читаются как UTF-8
без изменения переводов строк; перед запуском проверяются все контрольные суммы,
включая уведомление об авторских правах. Обычный запуск не использует сеть,
системные копии документов или Ruby.

* README Asciidoctor на английском, немецком, французском, японском и китайском:
  полные документы по 426–508 строк. Английский README дополнительно запускается
  с `env-github` и в safe mode с реальным `CHANGELOG.adoc` через
  `include::CHANGELOG.adoc[tag=compact,leveloffset=+1]`.
* Полный CHANGELOG Asciidoctor: 2210 строк.
* README adoctra из коммита `886b0a6`, без изменения исходного текста.

Итого семь исходных документов и девять приёмочных прогонов. Это первоначальный
корпус, преимущественно документация одного upstream-проекта, а не выборка всего
AsciiDoc. Семь дополнительных небольших документов проверяют диагностический
профиль и учитываются в отчёте отдельно от реальных документов.

Файлы Asciidoctor взяты из установленного Debian-пакета `asciidoctor 2.0.23-1`:
`/usr/share/doc/asciidoctor/README*.adoc.gz` и `changelog.gz`. Снимки — результат
распаковки без правок. Сохранён полный `COPYRIGHT` из этого же пакета с
уведомлением и лицензией MIT (Expat). Для adoctra сохранён полный id коммита;
диагностические примеры написаны в этом проекте и не выдаются за upstream-тесты.

== Проверяемый профиль

`body-dom-diagnostics-v1` сравнивает два независимых результата:

* `body`: прежняя проекция `body-dom-v1`, описанная в
  link:compatibility.adoc[контракте совместимости]. Весь документ сравнивается
  целиком; новые правила нормализации ради этого корпуса не добавлены.
* `diagnostics`: упорядоченный список `{severity, message}` для warning и более
  высоких уровней. Учитываются повторные сообщения и предупреждения HTML backend.
  Совпадение HTML при появлении нового предупреждения даёт FAIL.

Ruby launcher с `--report` использует `MemoryLogger` и возвращает JSON с HTML и
диагностиками. Сообщения ниже обычного порога WARN отбрасываются. У adoctra
разбираются существующие сообщения CLI и backend; неизвестная строка stderr
считается ошибкой стенда. В текстах сообщений заменяется только абсолютный
временный каталог fixture на `<fixture>`, с сохранением относительных путей.

Этот профиль не сравнивает позиции диагностик (файл, строку, колонку, byte spans),
полный ASG, атрибуты документа или точный HTML. Для них нужны отдельные профили.
Он также не проверяет время, память, WASM-размер или инкрементальность.

== Отдельный профиль структуры

`block-structure-v1` использует отдельный манифест
link:../compatibility/acceptance/structure.json[structure.json] и эталоны с
префиксом `structure-`. В нём повторяются девять прогонов полных документов
с теми же атрибутами и include-ресурсами; пять собственных примеров проверяют
блоки, разделы, списки, таблицы и отсутствие названия. Результат: *14 PASS*, отдельно от HTML и
диагностик. Примеры имеют SHA-256 и происхождение, но не являются upstream-тестами.

Ruby launcher с `--structure` вызывает `Asciidoctor.load` / `load_file` и
обходит дерево без конвертации и ленивых inline-подстановок. Adoctra запускается
с `--to json`; адаптер `scripts/structure.py` читает существующий JSON backend.
HTML не участвует в построении ни одного дерева.

Профиль сравнивает:

* наличие названия документа, контексты блоков, их порядок и вложенность;
* ID и упорядоченные роли блоков, уровни разделов и discrete-заголовков;
* простую/составную форму контейнера и тип admonition;
* вид списка, число и порядок элементов, состояние checkbox, вложенные блоки,
  число терминов и наличие описания в description list;
* число столбцов таблицы, группы head/body/foot, порядок строк и ячеек,
  стиль ячейки, colspan/rowspan и дерево вложенного документа AsciiDoc-ячейки.

Согласование представлений явно ограничено: первый heading уровня 0 adoctra
без стиля `discrete`/`float` становится признаком названия документа,
heading раздела передаёт ему метаданные,
а heading вне раздела соответствует `floating_title` Ruby. Единственный
синтетический параграф простого контейнера переносится в его `content_model`;
лишние дочерние блоки или метаданные этого параграфа не допускаются.
Отсутствующий colspan/rowspan означает 1. Неизвестный контекст или повреждённая
схема эталона/baseline останавливают стенд, а не исключаются из сравнения.

Это ограниченная проекция структуры, *не полный семантический ASG и не TCK*.
Не сравниваются текст и inline-узлы, содержимое заголовков, метаданные названия
документа, авторы/ревизия, большинство стилей и атрибутов, ссылки и их цели,
источники, позиции и диагностики. Диагностики проверяются прежним профилем;
неизвестный stderr и ошибки процессов остаются ошибками стенда в обоих профилях.
Изменение содержимого при неизменной структуре требует проверки HTML-профилем.

[source,sh]
----
python3 scripts/acceptance.py --manifest compatibility/acceptance/structure.json
python3 scripts/acceptance.py --manifest compatibility/acceptance/structure.json --verify-reference
python3 scripts/acceptance.py --manifest compatibility/acceptance/structure.json --json-report target/structure-report.json
----

Обновление эталонов и baseline выполняется теми же параметрами ниже, но с
`--manifest compatibility/acceptance/structure.json`. PASS/XFAIL/FAIL/XPASS и
проверка дрейфа действуют независимо для каждого профиля. Оба режима нового
профиля включены в CI. Расширение корпуса независимыми документами и
upstream-сценариями остаётся следующим шагом.

== Результат и известные отличия

Все девять прогонов реальных документов проходят. Диагностические примеры:
четыре PASS (порядок разделов, пропущенный атрибут, повторный id, неполная строка
таблицы) и три XFAIL:

* Незакрытый listing: adoctra выдаёт error и указывает отсутствующий разделитель,
  Ruby — warning с более коротким текстом.
* Неизвестная xref: adoctra выдаёт редакторское предупреждение, Ruby при обычном
  уровне журнала ничего не сообщает.
* Незакрытое условие: adoctra выдаёт редакторскую ошибку, Ruby при обычном уровне
  журнала ничего не сообщает.

HTML этих трёх примеров совпадает. XFAIL закрепляет весь текущий результат,
включая HTML и диагностики: новое расхождение внутри известного сбоя — FAIL,
неожиданное исправление — XPASS. Оба завершают стенд с кодом 1. Ошибка процесса,
таймаут, повреждённый fixture, неизвестный stderr и дрейф эталона — ошибка стенда
с кодом 2, даже для XFAIL. XFAIL не считается совместимостью.

Отдельное наблюдение при подборе корпуса: `docs/parser-api.adoc` из коммита
`886b0a6` вызывает в закреплённом Ruby `NoMethodError` в `restore_passthroughs`
при embedded-конвертации с `showtitle`. Этот кандидат не включён в корпус:
падение эталона нельзя считать PASS или ожидаемым отличием adoctra. Нужны
отдельное решение по включению документа и экранирование его намеренно ошибочных
примеров. Минимальное воспроизведение отказа Ruby — следующая строка (ошибка
возникает также внутри inline monospace):

[source,asciidoc]
----
latexmath:[$]
----

== Запуск и обновление

[source,sh]
----
cargo build -p adoctra-cli
python3 scripts/acceptance.py
python3 scripts/acceptance.py --verify-reference
python3 scripts/acceptance.py --case asciidoctor-readme-includes
python3 scripts/acceptance.py --json-report target/acceptance-report.json
python3 -m unittest discover -s scripts -p 'test_*.py'
----

JSON-отчёт содержит общий результат, отдельные счётчики категорий `document` и
`diagnostics`, результат каждой проверки `body` / `diagnostics` и причину XFAIL.
Оба запуска — offline и проверка настоящим Ruby — включены в CI рядом с прежним
корпусом из 3292 минимальных сценариев.

Новый документ добавляется полным неизменённым снимком с происхождением, лицензией
и SHA-256. Include-ресурсы должны ссылаться на такие же зарегистрированные файлы;
оба процессора получают одинаковое временное дерево с `main.adoc` в корне.
Пути вне корпуса и выход include-ресурсов за временный каталог отклоняются.

[source,sh]
----
python3 scripts/acceptance.py --case CASE_ID --update-reference
python3 scripts/acceptance.py --case CASE_ID
----

Обновление эталона не меняет `expect` или baseline adoctra. Известное отличие
требует причины, `expect: xfail`, анализа diff и отдельного явного действия:

[source,sh]
----
python3 scripts/acceptance.py --case CASE_ID --record-known-differences
----

При исправлении заменить `expect` на `pass` и удалить прежний baseline.
Не изменять исходный документ или правила нормализации, чтобы скрыть отличие.
